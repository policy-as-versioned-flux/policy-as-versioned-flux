## Reopened 2026-07-31 — Istio↔SPIRE CA bootstrap BLOCKED (fixed 2026-08-20 — see below)

Live bring-up (`verify-all.sh --live`) exposed two real bugs in this substrate:

1. **SPIRE chart 0.24.0 breaking value renames — FIXED (commit `f7f6732`).** Chart camelCased its values with hard `fail()` guards (`ca_subject`→`caSubject`, `caSubject.common_name`→`commonName`; the chart's own error text misreports the second as "ca_name"). The HelmRelease used the old snake_case names, so SPIRE never installed. Fixed → SPIRE now installs, all four pods Running.
2. **istiod CA bootstrap — FIXED (ticket mo-04, 2026-08-20).** This was misdiagnosed here as an istio-csr problem. There is no istio-csr or cert-manager anywhere in this repo; the `cacerts` / `istio-csr-ca-configmap` / `istio-csr-dns-cert` volumes named in the original diagnosis are unconditional `optional: true` volumes in the stock istiod chart and prove nothing. The real cause: `estate/platform/identity/istio/helmrelease.yaml` set `ENABLE_CA_SERVER: "false"`, and `meshConfig.trustDomain` and the sidecar-injection template wiring were missing. With `ENABLE_CA_SERVER` false and no istio-csr certs present, istiod never called `initIstiodCertLoader()`, so the bundle watcher stayed empty: istiod logged `Failed to load CA bundle: could not decode pem` → `patching webhook istio-sidecar-injector failed` → `cert not initialized`, and the sidecar-injection webhook returned `tls: internal error`, so meshed pods couldn't be created → no SVID → no workload mTLS. This blocked ticket 17's live positive path.

**Closed by ticket mo-04, 2026-08-20:** istiod now obtains a valid CA bundle + serving cert from SPIRE via the documented [SPIRE Workload API socket integration](https://istio.io/latest/docs/ops/integrations/spire/) (`spiffe-csi-driver`, not istio-csr), so the sidecar-injection webhook serves and meshed workloads start with real SPIFFE SVIDs — live-verified on `kind-driftwood`. What still blocks ticket 17's `verify-reach-secrets.sh` positive path is a separate, pre-existing `AuthorizationPolicy` scheme-mismatch bug: `principals` carries the full `spiffe://` scheme, which Istio's schema already prepends, so the rendered Envoy RBAC matcher is unmatchable and `ping`→`pong` 403s even though the mTLS handshake succeeds. This is not a CA-bootstrap failure and is tracked under ticket 11, not here. See `.scratch/multi-org-estate/issues/04-istiod-ca-bootstrap.md`.
