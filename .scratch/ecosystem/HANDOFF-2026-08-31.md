# Handoff, 2026-08-31 — everything is pushed, nothing is merged

The thin slice is built, committed and pushed across all nine repositories. Six pull requests are
open. **Merging is the one thing I could not do**, and it is the only thing standing between this
state and most of what is still amber.

## Do this first, in this order

Claude Code's permission classifier declines `gh pr merge`. Two different pull requests and two
different flag shapes gave the same refusal, so it is the action and not the invocation. To let a
future session do it, add one rule to `.claude/settings.json` under `permissions.allow`:

    "Bash(gh pr merge *)"

Then land the publishers **before** the adopters. The order is not a preference; the adopters
cannot pass CI until the publishers have released.

### Landing a pull request does NOT cut a tag

Checked on 2026-08-31, and it corrects what an earlier draft of this file implied. Every
`cut-release.yml` in all eight units triggers on `workflow_dispatch` **only**. Nothing fires on a
landing. After the publishers land you must dispatch each release by hand, or the checks waiting on
a tag stay amber for ever and nobody will know why.

Two tags are queued, and only two. Each repo declares its own next bump, and the gate refuses when
the declared and computed bumps disagree:

- **platform** -> `policy/v4.0.0`. Declared `bump: "major"` on the `versions.yaml` array element.
- **ico** -> `v3.0.0`. `penalty-schema/bump.yaml` says `major`. Its own comment says to set the
  file back to `none` once the tag exists.

Nothing else is queued: `nist/catalog/bump.yaml` and all five `feeds/*/bump.yaml` say `none`, which
is correct, because no content is waiting behind them.

Dispatch each with the workflow's single-tag form, giving the version and an annotated message that
says what changed and why. The gate runs, the evidence is signed and committed, and the tag is cut
inside Actions with a live gitsign identity. That signature is the one thing no local run can make,
which is why these checks were left amber rather than closed.

### Why the three adopters are red, and why you must not force them

Their CI composes through the **pinned** platform tag `v1.1.1`, whose party schema predates ticket
21. It rejects `size`, `appetite`, `publishes` and `reporting_currency` as unknown fields. That is
NORTH-STAR principle 4 working exactly as written: the publisher releases, then the adopter bumps
its pin. Land platform, let `cut-release.yml` cut its signed tags, bump each adopter's pin to the
new `{tag, commit}` pair, and the red goes away on its own.

## What merging does NOT fix

Four gaps are architectural. They need a decision, not a merge.

1. **Only one policy version is declared.** The retirement of 2.0.0, 2.0.1 and 3.0.0 was right —
   none of them could admit a pod — but it left `versions.yaml` with a single line. Coexistence,
   retirement and shift-left's plus-or-minus-one window all need a second declared version to have
   a subject. Each says so plainly rather than pretending to be pending.
2. **The conditional root-attested branch is gone.** It lived only in the retired
   `require-nonroot-2-0-1`. Neither 3.0.0 nor 4.0.0 inherited it. `verify-conditional.sh` now
   discovers this rather than naming a dead version, and it will pick the branch up automatically
   if a declared version ever carries it again.
3. **Federation has no peer.** There is no second SPIRE trust domain anywhere in the estate.
   Network reachability was tested and ruled out as the blocker: all three KinD clusters share one
   Docker bridge and a driftwood pod reaches the tuppence control plane directly.
4. **The observation-lane ruleset cannot exist.** GitHub refuses push rulesets on public
   repositories, verified against the real API: `Source public repos cannot have push rules`. The
   committed ruleset files are correct and inert. A reviewer also found that `required_signatures`
   would reject the very gitsign-signed bot commits it is meant to bless, because GitHub does not
   verify gitsign. Making this real needs a different mechanism or private repositories.

## One thing to check before you trust it again

`twin/enact_guard.py` had a hole: `_push_target` resolved a bare remote against the shell's own
directory, so `git -C <enactment repo> push origin <branch>` read **this** repository's origin,
matched the self-push carve-out, and admitted the push in silence. That is how eight branches
reached the world on 2026-08-31 while the mode said `operations`. It is fixed, with four tests,
three of which fail against the previous behaviour. The mode is back to `operations`.
