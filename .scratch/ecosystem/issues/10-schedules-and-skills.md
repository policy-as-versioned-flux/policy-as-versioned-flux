## Grilling round 1 — drafted 2026-08-28, HELD

Drafted AFK on the owner's instruction. Adversarially checked by two reviewers. Nothing below has been put to the owner. Five questions.

❓ **Q1** - **May a heuristic stand-in run inside a scheduled step**: the boundary rule is settled (twin decision 20 Q1). The live residue is what a clock may consume. The twin's daily sweep reads only committed claim files and never invokes a skill; platform's `wardley.py` computes editorial "ai-generated" forward rows on every run with no signed claim behind them (H5-04). Options: (a) never: a scheduled run consumes only committed grade-5 claim files landed by a reviewed PR; heuristic stand-ins run under the skill eval harness and as a skill a human invokes, nowhere else; (b) a stand-in may run inside a scheduled step as long as its output is labelled grade 5 with `model_version` recorded and is never consumed as evidence; (c) a stand-in may run on the clock until a model call replaces it, then moves to a skill.

➡️ (a). It is what the twin does already, so no second rule enters the eco-system, and it closes H5-04 by construction: `wardley.py`'s editorial layer becomes a committed, signed intel file that a human authored (or a skill wrote and a human merged) rather than a number the clock invents. (b) is the circularity H5-08 found, running unattended. (c) makes the boundary move on an implementation detail.

❓ **Q2** - **The period, and where the clocks live**: the three triggers are settled; the period and the placement are not. Today the only clocks are the hub's truth run, the hub's twin run (which sweeps a fixture and discards the result) and a failing in-cluster CronJob. Options: (a) one daily floor on every unit: the publisher fetch job, Renovate and `propose-tier` in each adopter, and each org twin's sweep each gain a `schedule:`, each org picks its own time, and the hub's 05:47 truth run grades whatever state exists when it runs; (b) a period per step: feeds as often as the source moves (endoflife.date hourly), proposals and sweep daily, truth daily; (c) a daily floor on the adopters only, publishers stay dispatch-driven until ticket 21 builds a real fetch.

➡️ (a). A daily floor is what makes "continuous" true on a day nothing is pushed (H4-02, H6-03), it is three lines per repo because the proposer is idempotent by construction, and Renovate belongs on the same clock because its PR is the only thing that starts a re-price. No cross-org ordering is promised: NORTH-STAR §2 says each participant ships on its own cadence, GitHub delays scheduled runs under load, and every joint in the chain waits on a human merge anyway; the truth run reports the state it finds. (b) multiplies cron lines nobody can reason about for feeds that do not exist yet. (c) leaves step 1 of the demo on a button. The currency-controller CronJob is ticket 13's.

❓ **Q3** - **Does the adopter's clock re-compose against unchanged pins**: composition runs only on `pull_request` and the proposer reads only the committed `composed/evidence.json`, so a scheduled `propose-tier` with no new PR would propose from stale prices. Prices already move with the date at fixed pins (EOL ramp by `--as-of`, stale size widening to the cap under ticket 07). Options: (a) yes: the scheduled run re-composes at today's date first, commits nothing, and proposes from the fresh `prices[]`; a date-driven band crossing with no new tag is a proposal trigger like any other; (b) yes, and the re-composed evidence is committed to main by the workflow so the truth surface can read it; (c) no: the clock only proposes from the last PR's evidence, and a price that moves with the date waits for the next pin bump.

➡️ (a). Ticket 07 already made the price a function of `as_of`, so a clock that does not re-price is a clock that reads last month's number; a proposal carries its own priced evidence in the PR (re-grill 15), so nothing needs committing to main. (b) is a machine commit to main with no reviewer, the thing re-grill 29 asked what stops. (c) makes principle 5's "cages re-price on a schedule" false in the one place it is cheapest to make true.

❓ **Q4** - **The publisher's clock and the declared bump**: ticket 04 A3 and re-grill 13 fix that the publisher declares the bump in a versioned file reviewed in a PR and the workflow reads it. The feeds repo is empty, no publisher computes a bump, and every `cut-release` is dispatch with a typed version. Options: (a) the scheduled fetch opens a PR in the feeds repo carrying the fetched payload and a mechanically computed declared bump (`payload_schema` change major, new entry minor, changed value patch); a human merges; `cut-release` runs on merge, reads the declared bump and tags with the Actions identity it already uses; (b) for pure data feeds (eol, cve, fx, market-moves) the clock commits and tags main directly, recorded as a supersession of ticket 04 A3 with the owner's reason, plus a ruleset bypass for the Actions identity on the feeds repo; (c) the clock opens the PR with the payload only and the human types the version, as `cut-release` works today.

➡️ (a). It keeps every settled rail (declared bump in the PR, author and merger different, no bypass), the tag signing already exists in six copies of `cut-release.yml`, and the bump computation is the one new piece, which ADR-0011 already does for policy on the platform side. The cost is honest: a source change reaches a cage through two human merges, the feed PR and the adopter's pin bump. (b) is a machine change reaching main unreviewed and a new exception to re-grill 29 for a feed whose only human is the one copying endoflife.date. (c) keeps a human typing a number a machine can compute. Forward-intel is not in scope: it is agent-signed and scheduled by ticket 08 A2. News with coordinates is ticket 23's.

❓ **Q5** - **The half-life, concretely**: re-grill 22 reversed count-based suppression. Today no adopter has a ledger and all three read platform's fixture; whichever option wins removes the `DEFAULT_REJECTIONS` fallback. Options: (a) the ledger is derived at run time from closed-unmerged PRs on the proposal's dedupe branch (`gh pr list --head --state closed`); suppress while `sum(0.5 ** (age_days / h))` over those closes is at or above `reject_suppress`, so one rejection suppresses for under `h` days and repeated rejections suppress longer; a rejected PR whose recorded curve hash and selection-policy version (ticket 08 A4) differ from today's proposal does not count, because a new £ is a new proposal; (b) the same function over a committed `rejections.json` in the adopter repo that `propose-tier` appends to on PR close; (c) time decay only, no reset for a new £: the same slug re-raises when the summed weight falls below the threshold whatever the number is.

➡️ (a). The PR record is the only record, so there is no writer to build and nothing an adopter can edit without a PR; the dedupe branch already keys it and the PR body already carries the curve hash, so "a different proposal" is a hash mismatch, not a judgement. (b) adds a committed file that can drift from the PRs it summarises. (c) makes a rejection of £2,000 suppress a proposal of £20,000. The half-life value `h` is a versioned calibration knob beside `twin/decay.yaml`'s 180, not a decision today.
