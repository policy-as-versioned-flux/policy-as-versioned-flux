"Earliest run where grade began" methodology: I ran a single `git log --format --name-only -- talk/captures/`
on `origin/main` (`../understand/captures-fulllog.txt`) and, for each platform capture file, took the
**most recent commit in which that exact file's bytes changed**. History only goes back to run 9
(the commit that introduced the captures/ mechanism, ticket 20 D1/Q2); run 14 does not exist in this
history (skipped/not recorded). A file whose bytes are identical from run X through run 21 is reported
as "since run X" — this is a **content-identity** proxy, not a re-run confirmation that the grade itself
was unchanged at every intermediate run (a script that embeds no timestamp/PID/random ordering could in
principle produce identical bytes for two different real-world states across two runs — I did not audit
every script for that possibility). Where I list "since run 12" or "since run 9" that is this proxy's
floor, not a claim I watched the exact run number when the underlying beat first went green.

## Section A — the 13 scripts that hard-code the persistent `kind-driftwood` cluster

All 13 `source ../lib.sh` (or `../../lib.sh`) and set `CLUSTER="${CLUSTER:-driftwood}"`. `lib.sh`'s
`substrate_ok()`/`require_substrate()` correctly `skip()` (echo `SKIP: ...`, `exit 3`) when
`kind get clusters` does not list `driftwood` — so on a CI runner (which never has this persistent
kind cluster) these 13 **always** land on the live tail's SKIP branch; only the offline half is ever
observed. This is the honest, gated behaviour lib.sh documents (three outcomes, no fake PASS on
absence) — I found no false-PASS defect in lib.sh itself.
