## 3. "cross-org reads are structurally unreachable from a single-repo runner token" — **FALSE**

This is the clause I set out to break, and it breaks.

All nine repos are **public**:

```
$ for o in platform driftwood feeds insurer nist ico ludlow tuppence; do gh api "repos/policy-as-versioned-$o/$o" --jq .visibility; done
public × 8      (hub policy-as-versioned-flux/policy-as-versioned-flux: public)
```

Both API endpoints the live half needs answer **anonymously, with no credential of any kind**,
across the org boundary:

```
$ curl -s -o /dev/null -w "%{http_code}\n" "https://api.github.com/repos/policy-as-versioned-driftwood/driftwood/actions/workflows/propose-tier.yml/runs?event=schedule&per_page=1"

$ curl -s -o /dev/null -w "%{http_code}\n" "https://api.github.com/repos/policy-as-versioned-driftwood/driftwood/contents/.github/workflows/propose-tier.yml"
200
```

(`schedules.py:466` `gh run list --repo ...` and `schedules.py:489` `gh api repos/<remote>/contents/...`
are the two calls; both map onto those endpoints.)

And the anonymous read returns the exact fact the SKIP says it "cannot look at":

```
$ curl -s ".../actions/workflows/propose-tier.yml/runs?event=schedule&per_page=2" | jq
2026-09-02T11:43:35Z completed success
2026-09-01T12:01:05Z completed success
```

driftwood's propose-tier clock **did** run inside its period. I observed it from a primary source,
right now, with no token. So the blindness is not structural, it is a wiring choice: the check
aborts at `gh auth status` (`schedules.py:509`) and never attempts a read. `gh` refuses without a
token as a CLI policy, not because the API refused:

```
$ env -u GH_TOKEN -u GITHUB_TOKEN GH_CONFIG_DIR=<empty> gh auth status

```

The owner's own record agrees with me and not with the auditor.
`.scratch/ecosystem/issues/56-the-citable-run-can-see-whether-the-clocks-ran.md` prescribes
"a read-scoped credential isolated from the untrusted verify scripts ... or an equivalent design
that keeps the token out of the eight orgs' unpinned scripts". Nobody who thought the read was
unreachable would write that ticket. Ticket 56 is **open**, `Blocked by: none`, and its Question
opens with the same sentence the auditor's claim opens with — so the finding is a faithful
restatement of an already-owned item, which the auditor does credit.

## 4. "The capture's last non-empty line is one of these SKIPs, so the whole script grades SKIP" — mechanism wrong

Grading is by **exit code**, not by the last line. `talk/verify-all.sh:58,62-66`: `rc=$?` then
`case $rc in 0) PASS ;; 3) SKIP ;; 124|*) FAIL`. Line 60's `last="$(tail -1 "$cap" ...)"` is only
the reason string printed beside the verdict. The chain is
`schedules.py` exit precedence ("any FAIL -> 1; else any SKIP -> 3; else 0", docstring `:30-31`)
→ `verify-schedules.sh:44-50` passes that rc straight through → verify-all.sh buckets on it.

This matters for a second reason: `verify_schedules` would grade **SKIP even with GitHub
reachable**, because three non-live SKIPs are also in the capture — ico, nist and platform
`fetch.yml` "opens no pull request anywhere ... story 9 / D2 is not implemented here"
(`schedules.py:537-546`). Closing ticket 56 alone does not turn this script green.

## 5. "A clock that stops firing produces no red anywhere" — essentially right, with one nuance

`grep -rniE "stale|freshness|too old|max_age|PERIOD_HOURS" verify/` finds only three sites:
`schedules.py` (the blind half), `pound_seam.py:332` (a retired-file check, not a clock), and
`verify/e2e/verify-e2e-step4-flux-reconciles-cage.sh:62`, which grades the drift-sample lane with
`--max-age-hours ${FIVE_FACT_MAX_AGE_HOURS:-48}`. So one clock — `drift-sample.yml` — does have a
freshness bound in the gate. But a stale sample returns **exit 3**
(`driftwood/drift/five-facts.py:646-648`: "SKIP: the newest five-fact sample is Nh old ... older
than the 48h freshness bound"), which `verify-all.sh` buckets as SKIP, not FAIL, on the citable
(non-`--live`) run. So: no red, but the skip/pass counts on the TRUTH line would shift. The
auditor's sentence survives; "produces no red, though it would move a PASS into the skip bucket"
is the exact version.

Note also that `drift-sample.yml` is **not** in `need` (it draws cage PASS lines in the capture but
no "daily clock at ..." line and no live SKIP), so it is the one clock with any liveness pressure
on it at all, and that pressure is indirect.
