## What does not hold

### A. "a new policy version can never raise a dependency PR at any adopter" — false, it did, three times

`git -C units/platform show v1.1.1:distribution/versions.yaml | grep '{ version'`:

```
- { version: "2.0.0", tag: "policy/v2.0.0", commit: "fa862b7..." }
- { version: "2.0.1", tag: "policy/v2.0.1", commit: "a1072d9..." }
- { version: "3.0.0", tag: "policy/v3.0.0", commit: "fa862b7..." }
```

`git -C units/platform show v2.0.1:distribution/versions.yaml | grep '{ version'`:

```
- { version: "4.0.0", tag: "policy/v4.0.0", commit: "64635df...", bump: "major" }
```

And Renovate raised exactly that step at all three adopters:

| PR | author | created | closed | body change |
|---|---|---|---|---|
| driftwood #13 | app/renovate | 2026-08-31T16:23:23Z | 16:24:21Z | major `v1.1.1` → `v2.0.1` |
| tuppence #10 | app/renovate | 2026-08-31T16:23:15Z | 16:24:33Z | major `v1.1.1` → `v2.0.1` |
| ludlow #9 | app/renovate | 2026-08-31T16:23:30Z | 16:24:42Z | major `v1.1.1` → `v2.0.1` |

The entire content of that machine-raised PR is a policy-version change: retire 2.0.0/2.0.1/3.0.0,
install 4.0.0. So a new policy version demonstrably *can* and *did* raise a dependency PR at every
adopter. What actually happened is that a hand-made commit beat it —
`git -C units/driftwood log -- gitops/platform/platform-pin.yaml` shows `7c55463` (chrisns,
2026-08-31 16:10:15, "adopt platform v2.0.0") and `e0eaa01` (17:19:59, "pin platform v2.0.1");
ludlow the same at `146dff7`/`fdfa386` — so Renovate autoclosed its own PR as already-done.
The defect is *never merged*, not *never raisable*.

### C. "in either implementation" — false for the 2022 thesis org

`gh api /repos/policy-as-versioned-flux/fleet/contents/renovate.json` decodes to a customManager
with `"depNameTemplate": "https://github.com/policy-as-versioned-flux/policy"`, `git-refs`,
`semver`, over `/^clusters/.*\.yaml$/` matching the `{tag, commit}` pair — i.e. the 2022
implementation **is** wired for policy versions directly. And it fired:
`gh pr view 21 -R policy-as-versioned-flux/fleet` → OPEN, created 2026-07-16T12:18:54Z by
`app/renovate`, branch `renovate/https-github.com-policy-as-versioned-flux-policy-2.x`,
title "Update dependency https://github.com/policy-as-versioned-flux/policy to v2.2.1",
body "patch `2.2.0` → `2.2.1`". So the loop was wired and a policy-version PR was raised there;
only the merge never happened.

### D. Framing it as unowned drift misreads a recorded decision

The adopters do not pin policy versions **by decision**, so a `policy/v*` manager would pin a
dependency they do not have:

- `.scratch/ecosystem/issues/16-flux-rescoped-and-verified-at-the-cluster.md:55` Q5 answer (c),
  resolved: "…the `policy/v*` fan-out sources are platform-internal and are not compared".
- `docs/adr/0012-composed-artefact-self-signed-pinned-sha.md:7-14` — the adopter's own package is
  its signed `composed/` set, rendered from pinned parent SHAs.
- ticket 18:30 states the mechanism positively: "Policy-line elements reach adopters as the whole
  `versions.yaml` array on the next platform `v*` bump."
- `.scratch/ecosystem/bump-adopter-pins.sh:4-6` and `.scratch/ecosystem/HANDOFF-2026-08-31.md:7-9`
  both say it outright: "the adopters pin `{party: platform, kind: implementations}`, which is the
  bare tag… not `policy/v*`".
- `units/driftwood/party.yaml:51` — `{ party: platform, kind: implementations, version: "2.0.1" }`;
  `units/driftwood/composed/HEADER.yaml:6-9` records the same parent. All three adopters'
  `composed/policies/` contains exactly `v4.0.0`.

Mechanically there is also nothing cross-repo for Renovate to bump on the policy line: the array
lives in the *same* repo as the policy trees (`units/platform/distribution/versions.yaml`), written
by `cut-release`, and `find units -iname '*renovate*'` shows platform carries no renovate.json at
all (only driftwood, tuppence, ludlow, insurer do).
