## 1. The mechanism holds

`compose/composition.py:1934-1981` (`compute_prices`) — verified verbatim. It loops feed edges and
calls `price_parent(edge, adopter_party, tolerance, ...)` at 1964-1967 once per edge, then
`price_twin(adopter_dir, adopter_party, tolerance, ...)` once at 1977. The same scalar `tolerance`
reaches every call.

`price_parent` (1520-1609) converts the band to the publisher's currency at 1571-1572 —
magnitude unchanged — then `cage.select(old_sc/new_sc, adopter_party, band_native, ...)` at 1574-1575.

`price_twin` (1690-1795) does the same at 1755 (`band, _ = _converted(tolerance, ...)`) and hands
the whole band to the adopter's own selection package at 1761-1763.

**Correction to the citation.** The finding cites `cage.py:171-181`. `select_tier` is `def` at
**cage.py:173**; the comparison the finding is about is **cage.py:182-187**:

```
182	    for tier in ORDER:
183	        if caged_residual(uncaged_ale, tier) <= tolerance:
184	            break
185	    else:
186	        tier = ORDER[-1]
```

`171-181` lands on `tcor()`'s tail and the docstring, and misses line 183 entirely. Substance
unaffected — one line's caged residual against the whole band, no other term.

driftwood's own package does the same: `selection-policy/selection_policy.py:88`
`under = [t for t in LADDER if t in priced and priced[t] <= limit]`, where `limit` is the full
`tolerance["amount"]`.

## 3. Two corrections that make the finding stronger, not weaker

**(a) A non-fitting line is indistinguishable from a fitting one.** `price_parent` records no basis
string (compare `price_twin`, which carries `policy_basis`). At tuppence and ludlow the same
mechanism produces lines that fit nothing and still print as a bare `proposed_tier: isolated`:

```
tuppence (appetite 15,000): ico residual=180795.82 fits band? False | threat 4451.49 True
                            SUM=185247.31  ratio=12.35
ludlow   (appetite  5,000): ico residual=180795.82 False | threat 6364.60 False
                            SUM=187160.42  ratio=37.43
```

(amounts read from each unit's `composed/evidence.json`.) Relatedly, `cage.select`'s human-readable
`reason` at **cage.py:217-221** appends `"(fits band £{tolerance:,.0f})"` unconditionally — it says
"fits band" for a residual that does not. So the finding's forward claim ("a fourth priced parent
would raise the retained total with every line still green") is not an extrapolation; the estate
already carries lines that are over the band and print green.

**(b) The insurance objection does not survive.** driftwood holds a quote attaching at exactly
40,000 with a 3,000,000 limit (`evidence.json` premium entry), so a defender could argue the excess
is transferred, not carried. Nothing computes that. CONTEXT.md:311-312 promises "the sheet shows
retained, transferred and excluded loss summing to the simulated total"; grepping
`transferred|retained_loss|excluded_loss` across the insurer, platform and driftwood trees returns
only a comment (`platform/tcor/tcor.py:252`). No implementation exists.

## 4. Is there aggregation anywhere? No aggregate-vs-band test anywhere.

- `exposure_section` (composition.py:1882-1931) does aggregate the **uncaged** amounts:
  `composed/HEADER.yaml` shows `total: 3704381.737952101` beside `attachment: 40000.0`. So the
  estate does publish an org-level exposure total — but it is pre-cage, and nothing compares any
  **residual** total to the band.
- `platform/tcor/tcor.py:141-160` `balance_sheet()` sums residuals across a portfolio into a total,
  but never tests that total against the tolerance, and each row still calls
  `cage.select_tier(ale_behind, tolerance)` (tcor.py:110) with the full band. It runs on one
  hand-authored fixture and is not on the composed path.
- `verify/pound-seam/pound_seam.py` checks per-entry hole sums, perspective/currency purity and
  that the two selection engines agree at the boundary. No aggregate-vs-band assertion.
- `composed/evidence.json` `cages: []` — driftwood has no cage applied today. These are *proposed*
  tiers (`proposed_as: "label"`), so "retained" is the model's word (cage.py:167 `# R' — retained,
  priced, still positive`), not a description of running workloads.

## 5. Ownership: the finding's claim holds, and the contradiction is sharper than stated

Only one ponytail note is anywhere near this — `composition.py:1895` "ponytail ceiling: the total is
the sum of the priced parent edges, not an aggregate loss DISTRIBUTION ... Upgrade path: fair.py
gains a portfolio aggregate". Verified verbatim. It is about the exposure *total's shape*, not about
the tier selection spending the band per line. Grepping `ponytail` across the platform repo for
band/tolerance/appetite/aggregate/portfolio/tier returns nothing else relevant.

  aggregate".

So this is not an undecided design question the finding is inventing a standard for. The

contradicts it. `NORTH-STAR.md:32` is confirmed verbatim as the finding quotes it.

## 6. Double-count caveat (does not sink it)

The twin entry carries `"lef_from": "threat-register"` and the same `lef: [2,4,9]` as the
threat-register line; both model cart/checkout PII exfiltration under different consequences. If a
reader refuses to sum those two, the most conservative retained total is
35,743.54 + 37,952.92 = **73,696.46 = 1.84x** the appetite. The estate itself sums all three into
`exposure.total`, so 2.18x is consistent with the estate's own treatment — but 1.84x is the floor.
