# 00 — The constitution

Every build ticket's reading list includes this file. It is short on purpose: the point is that a
fresh context can absorb the whole thing cheaply and still have its window for the actual work.

## The invariants

Refusal tests at seam 1. Most of this system's non-negotiables are **absences**, and an absence never
shows up in a diff — a new feature does, a removed refusal does not.

`no_collapse_mechanism` · `no_recommended_action_field` · `no_special_category_slot` ·
`world_never_references_overlay` · `as_consumed_admits_no_post_T_fact` · `grade_5_only_path_never_prices` ·

`standing_library_covers_committed_classes`

Each has an activating ticket in the manifest (build ticket 02). An invariant still pending after its
activating ticket has closed is a CI failure.

**Every ticket extends the suite and never weakens it.** A ticket that genuinely needs an invariant
changed must name it and cite the authorising decision ticket. Test bodies are hashed; a hash change
without a citation fails CI.

## The five refusals to collapse plurality

These look like separate design choices and are one thing. **A single number ends a conversation; a
map sustains one** — the point of the artefact is to be argued with, distanced from the human stories
and the emotion, so terminating the argument would destroy its function.

1. Competing **world models** coexist as first-class units.
2. Rival **causal accounts** coexist as ensemble spread, adjudicated by calibration over time.
3. An execution emits **multiple forecasts**; nothing collapses them.
4. Output is a **trade-off curve with a marked default**, never a verdict.
5. **Contestability** is a primary workflow, not a complaints box.

## The three named failure modes

- **Skeleton-as-ceiling** — the thin slice quietly becomes the definition of done. Guard: each
  decision ticket's **full** acceptance criteria remain the yardstick; a build ticket satisfies a
  *slice* and never redefines them.
- **Premature done** — a stub marked complete. Guard: depth grades are **computed checklists**
  against the owning decision ticket's ACs. `full` is derived, never typed.
- **Sunk-cost architecture** — early code shapes later decisions because rewriting feels wasteful.
  Guard: **code is disposable by default.** The durable artefacts are the versioned model and the
  decision record; code is nearer derived than authored, so replacing it is normal.

## The continuous coherence mechanism

The **pocket-org golden fixture** (build ticket 15): a hand-computable org with its expected numbers
worked out by hand in a committed worksheet. Refusal tests catch reintroduced absences; the pocket
org catches **silently weakened presences** — a PERT triple present but garbage, a score tagged with
the wrong regime, a discount hardcoded rather than measured. Every ticket touching the derivation
path adds its worksheet line and keeps the rest green.

## The boundary fixtures

Generated by the earlier track's code in CI, never committed once and left to fossilise: the **graph

## The three seams

1. **The artefact CLI** — primary. Golden-file testable because attestation already demands
   determinism given the pins.
2. **The typed model API** — thin, below the CLI. Numerical and structural properties only, never
   call sequences or object shapes. Exists because a propagation defect and a validation defect are
   indistinguishable at seam 1: both are "wrong number".
3. **The skill-eval harness** — the six skills are non-deterministic by construction. Threshold
   scoring against fixture corpora, recorded per skill per model version.

A test coupled to internals becomes the sunk cost that resists the rewrite. Assert on external
behaviour at a boundary — an emitted artefact, a validated claim, a score.

## The critical path

Not the track count — the **critical path** sets the calendar. Computed from the blocking graph, it is
**20 tickets long**:

`01 → 02 → 03 → 04 → 05 → 06 → 07 → 12 → 26 → 27 → 28 → 29 → 65 → 66 → 67 → 68 → 70 → 73 → 74 → 77`

Worth reading, because it is not the chain you would guess. It runs **foundations → skeleton →
schema → the perspective/constraint/pricing chain → the whole enactment arm → the full-system audit
→ the Netflix beat**. Enactment is on the critical path because the Flux verdict (65) needs
causally-gated pricing (29) to state the risk basis, and everything downstream of the verdict
serialises; the beats then wait on the confirmatory audit (70), which waits on enactment.

Two consequences worth acting on rather than noting:

- **The causal and time chains are *not* the constraint.** Propagation, regimes and backtest have
  slack. Spending effort shortening them buys nothing.
- **The £ chain is deliberately parallel to propagation**, not behind it — both meet at the pocket-org
  fixture (15). That was the largest available cut and it is already taken. The next largest is
  relaxing `66 ← 65`: the propose-only PR channel does not need the Flux verdict, only the
  policy-pinning half does. Split it if the calendar matters.

Only one ticket starts immediately (01). After 04 the openable set is 05, 10, 42 and 64 — provenance,
skills and Flux drift measurement run genuinely parallel from there, and 64 is deliberately early
because it needs elapsed calendar time and nothing from the twin.

## Wait, plant, or force — in that order of suspicion

Added 2026-08-14, from build ticket 78. A ticket that needs real-world evidence and reaches for a
long passive wait should check one thing first: can the same real system be made to produce the
evidence now, on purpose, faster — rather than either waiting on it to happen unprompted, or
generating a synthetic stand-in for it?

**A passive wait is the default and the weakest excuse to skip.** It is real evidence, but slow, and
on a system with no genuine operator population behind it, a wait can end in a null result that
means "nothing happened" rather than "nothing happens" — build ticket 64's own limitation.

**A synthetic stand-in is refused when the same model family would generate and grade it.** Decision
ticket 12 Q2 already found the failure mode: shared priors mean a synthetic result evidences the
detection machinery, never the world. This does not change per-ticket; it is a structural limit on
what synthetic evidence can ever claim to be.

**Forcing the real system is preferred when it is available.** A bounded, scripted, reversible
action against the real system under test produces real data about a real mechanism, faster than
waiting and without the shared-prior ceiling — at the cost of answering a *mechanism* question
("does the system catch a known change, and how fast") rather than the *base-rate* question a
passive wait answers ("does this happen unprompted, and how often"). The two are not
interchangeable and a ticket citing this section states plainly which one it is answering.

## A pre-registered threshold needs a reachability guard, not only a liveness one

Added 2026-08-15, from build ticket 70. A pre-registration that names a threshold also names a
**deadline nobody wrote down**: the last moment at which the instrument can still reach it. Miss that
moment and the measurement is settled, whatever the instrument does next.

Build ticket 70 found this live, and the interesting part is that **nothing was hidden**. Ticket 64
recorded "NOT MEASURING" and named the missing crontab; ticket 65 recorded "1% coverage". Both were
honest and neither was green. What no file carried was that the shortfall would **expire**: ticket
64's guard asks "did a sample land today", which a daily hand-run satisfies at 4% coverage, and
ticket 65 reads coverage only after the window closes. A rate reads as recoverable. **"We are
behind" and "there are ten hours left" are different facts, and only the first was ever computed.**

So: any ticket that pre-registers a threshold against a sampled instrument states, in code, the
moment that threshold expires, and fails while there is still time to act. `twin/drift.py`'s
`floor_reachable()` is the worked example. A guard that only fires when the answer is already lost
is a record, not a guard.
