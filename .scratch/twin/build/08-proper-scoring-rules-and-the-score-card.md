# 08 — Proper scoring rules and the score card

**What to build:** Brier and log scores, regime tagging on every score, and the score card as a real artefact.

**Moved deliberately to directly after the skeleton.** An earlier draft of this plan blocked scoring
behind the whole causal and time chain, which contradicts the spec's own reason for putting scoring
in the first slice. Proper scoring rules need a forecast and an outcome — nothing else.

**Blocked by:** 07

**Status:** done (2026-08-05)

**Reading list:** Decision tickets 08, 11, 19. Spec stories 40, 44.

- [x] Brier and log scores implemented with property tests (proper-scoring behaviour under a shifted forecast).
- [x] Every score carries an information-regime tag; `only_as_consumed_scores` goes live even though only one regime exists yet.
- [x] The **answer-key fixture format** is defined and committed here — the boundary fixture the answer-key track tests against.
- [x] A score is refusable: a forecast with no resolvable outcome yields an explicit unscoreable result, not a zero.
- [x] Extends the invariant suite; never weakens it. Any invariant change names the invariant and cites the authorising decision ticket.
- [x] Declares its depth grade as a **computed checklist** against the owning decision ticket's acceptance criteria — `full` is derived from the checklist, never asserted.

## Built (2026-08-05)

`twin/scoring.py`, and the score card in `twin/verbs.py`.

- **Propriety is asserted numerically, not by naming the formula.** `tests/test_scoring.py` checks, over
  a grid of true probabilities, that no other forecast beats reporting the truth — for both rules. That
  is the definition of a proper scoring rule, and it is the only reason to use one.
- Both rules are losses and the card says so (`orientation: lower-is-better`), so nothing downstream has
  to guess. Both are emitted; collapsing to one is the reader's choice, never this code's.
- **A claim of certainty is refused where it is authored.** A belief of exactly 0 or 1 carries an
  infinite log-score penalty, which is not serialisable — so the schema rejects it rather than the
  scorer discovering it later.
- **The regime tag is real, and the refusal is real.** Every forecast carries its information regime and
  only `as-consumed` scores; a bundle executed `as-knowable` or `with-hindsight` produces an explicit
  unscoreable result and **no number at all**, because a zero would read as a confident forecast that was
  wrong. The *gating* — refusing a fact dated after T — is build ticket 36, and the artefact says so
  rather than implying otherwise.
- **The answer-key format is committed**, with `contamination` and `source_dated` **required**: the
  memorisation discount (build ticket 40) is computed from the contamination class, and an answer key
  that does not declare one silently becomes "assume it is clean", which is the assumption the discount
  exists to refuse.
- Unscoreable is a first-class result with a reason, never an omission and never a zero.

Not built: reliability diagrams over volume (09), the contamination discount itself (40), hindsight-
resistance inversion (41). The regime tag has one usable value until 36.

## Review round (2026-08-06)

- **The regime default was the wrong way round.** A forecast carrying *no* regime defaulted to
  `as-consumed` and scored, and the card then stamped it `as-consumed` — a tag the bundle never made.
  So `only_as_consumed_scores` could be bypassed by **deleting** the tag rather than changing it, which
  is why the invariant never saw it: it only ever rewrote regimes to another value. There is no default
  now; an untagged forecast is unscoreable. The execution's own `scoring_eligible` is read back too.
- **A bundle from another tenant could be scored** into this tenant's card, carrying the other org's
  probabilities verbatim. Propositions live in the shared world layer, so a proposition match was never
  a tenancy check. Refused.
- **A mutation survived**: replacing the `no-resolvable-outcome` refusal with `brier: 0.0` left both
  suites green. Nothing referenced `unscoreable` in any test. Covered now, including that no number
  appears anywhere in an unscoreable entry.
- **A probability outside (0,1) in a bundle crashed the scorer** with a bare traceback, in a tool whose
  CLI comment says a refusal is a sentence and not a stack dump. Refused as `not-a-probability`.

Note on the fixture wording: this ticket says the answer-key format is "defined and **committed** here",
while the constitution lists the answer-key fixture among those "generated by the earlier track's code
in CI, never committed once and left to fossilise". What is committed is the **schema**; the fixture
instance is generated by `twin/fixtures.py` on every run, like the rest.
