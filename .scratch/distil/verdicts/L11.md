### 2.2 The veto rule in code is the opposite of the target's

The target says "a closed one is a veto until an input changes". `rejection_ledger.py` does three different things:

- **It forgets.** Its own selfcheck asserts that one rejection "re-raises after h days", with h = 30 (`rejection_ledger.py:199-203`, `rejection-decay.yaml:21-23`). A veto lapses after about a month whether or not anything changed.
- **"Input changed" reads only the twin.** `fingerprint()` reads `curve_hash` and `policy_version` from the `source: twin` price line and nothing else (`:97-110`). With the twin parked, the fingerprint is always empty. Empty equals empty (selfcheck `:247`), so a new feed tag, a new probe result or a new tolerance would *not* lift the veto. Only time would.
- **The window is short.** `closed_unmerged` asks `gh` for the last 100 closed PRs and only then keeps unmerged ones on `wargamer/` branches (`:118-130`). Merged Renovate and inventory PRs count against the 100. driftwood has 127 merge commits on main (map A4), so an old veto can fall out of the window.
- **Offline, it proposes.** When the PR list cannot be read, the ledger is empty and the proposer proposes, saying so (`:24-28`, `:160-167`). The target says could-not-look means no move. A release proposal must not be opened when the vetoes cannot be read.

So the check "a closed pull request is still a veto, as a test" cannot be met by lifting this file. It needs a new rule and a new test.

What is worth keeping from it:
- The veto is derived from closed, unmerged PRs and never from a committed file. Commit 57e3e9f records why: every adopter had been reading platform's `rejections.json` "as its own history and would have been suppressed by a rejection it never made".
- The PR body carries a marker naming the question (`MARKER`, `:51-56`; `parse_marker`, `:92-94`).
- A merged PR is not a rejection, and an off-branch PR is not a proposal (selfcheck `:221-224`).
- Another organisation's rejection does not count (`:217-218`).

- `validate()` imports `inventory_ids` from `platform/feeds/to_fair_scenario.py` (`:173-174`).

This is the one proposer whose PRs have reached main: driftwood PRs #67, #78 and #93 (merges 5c5e4de 2026-10-17, 486f0c7 2026-10-21, bd5d5b9 2026-10-28; `git log` on driftwood). The scan logic is live and worth keeping. The pin rule needs one change: read the commit Flux reports as applied, not a tag.

**Write new, using lessons from here:**

- **The veto.** Derive it from closed, unmerged release PRs on one fixed branch name. Use a body marker whose fingerprint hashes every input the loop reads: feed tags, cage version, the last probe result per rung, tolerance and `party.yaml`. It never decays. If the PR list cannot be read, that is could-not-look and no release is proposed. Page through the list, or query by head branch, rather than taking the last 100 closed PRs. The test must assert that a closed PR still vetoes after 30 days, and that one changed input lifts it.
- **The never-merge guard.** Keep the AST scan over `loop.py` for merge, approve and close verbs (`tier_pr.py:276-311`, with the plant at `:314-320`) as one test. It matters because the loop writes tightenings itself while a person must merge every release.
- **A Monte-Carlo cross-check in tests,** with Poisson counts in place of `round()` (`fair.py:160`).
