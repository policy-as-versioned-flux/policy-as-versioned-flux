# L12 verdict: Platform, the cage (`platform/graded/`, `platform/distribution/`)

Verifier, read-only, 2026-11-14. Paths are under `scratchpad/fresh/` (remote default branches, platform HEAD 7beb126). "HEAD reader" means code that reads the platform working tree on main. "Pinned reader" means code that reads a signed tag or an adopter's own copy, which survives whatever happens to main.

Measured: 100 files, 10,680 lines (`find graded distribution -type f | xargs wc -l`).

Terms used below:
- **Governed Namespace:** a Namespace labelled `policy-as-versioned.dev/governed: "true"`. Only a governed Namespace may declare a rung, through the label `posture.acme.io/tier`.
- **Claim:** a pod's label `policy-as-versioned.dev/policy-version: <v>`. Served cage bodies act only on pods that claim their own version.
- **Machinery:** the eight version-less documents that `distribution/versions.yaml` renders beside the versioned trees. They are the orphan guard and its two cages, the governed-namespace cage, its hold and its report, the bottom-rung reach generator, and an unsuffixed `cage-isolated` PriorityClass.
- **Substrate:** the cluster's own system Namespaces and pods: kube-system (CoreDNS), flux-system, kyverno.

## Verdict in one paragraph

On today's chain the loop does **not** run without this component. The composer hard-imports `graded/cage.py` and reads `distribution/` (versions array, policy trees, `cage_body.py`, machinery). On the target chain nothing imports it: `loop.py`, `probe.py` and `inventory.py` do not need `cage.py`, the reduction table, the renderers, the fan-out or the old trees. But the target still needs a cage. The only cage that exists, and the only record of about a dozen defects found live on a cluster, are the two authoring bodies in `graded/policies/` and their Kyverno fixtures. So the second attempt (it breaks or loses something) succeeds for a small, named part, and the first attempt succeeds for everything else. Recommendation: **shrink**. Keep `cage-tier` and `cage-netpol` (plus their test matrix) as the seed of cage version 8 and carry their lessons into it. Park the rest. Every tag stays.

## Second attempt: show the loop breaks or loses something

The part that succeeds here is small, and it lives only in this component.

1. **The cage itself.** The target lists "cage version 8: two Kyverno bodies". No v8 exists: `git log --all -- distribution/policies/v8.0.0` returns nothing. Its only source is `graded/policies/cage-tier.yaml` (304 lines; served shape 43 lines in `distribution/policies/v7.0.0/cage-tier.yaml`) and `graded/policies/cage-netpol.yaml` (134 lines; served 45). Without them, v8 is written from nothing.
2. **The rung's output label, which the probe reads.** `cage-tier` clobbers `posture.acme.io/tier` and stamps `posture.acme.io/caged` on every pod from the Namespace (`graded/policies/cage-tier.yaml:243-247`). The target's probe "reads the rung on every pod", and the rule "no new notch until every governed pod is observed at the last commanded rung" depends on that label.
3. **Fail-closed default.** `cage-tier.yaml:188-218` (served `v7.0.0/cage-tier.yaml:31-34`): a Namespace that is ungoverned, has no tier or has an unknown tier renders `isolated`. Commit 60c02f8 (ticket 63) made that flip.
4. **The lessons, observed live, that a loop which actually moves rungs will hit again.** They are listed under "must absorb" below. Each one is a fix to a defect that was observed on kind-driftwood or measured under Kyverno 1.18.2, not argued from the code.
5. **The test matrix.** `graded/tests/cage-tier/values.yaml:7-49` has seven Namespaces: four rungs, untiered, ungoverned, and ungoverned-but-labelled-baseline. With `patched.yaml` it is the consumer test's starting point. `graded/tests/cage-netpol/` covers reach for each rung.

## What the target loop must absorb (each with its source)

Status on all of these: "not observed under a moving ratchet". No run has ever moved a rung (A4, hop 5).

1. **The priority trio.** A mutating webhook that writes `priorityClassName` must also write `priority` (equal to the class's `value`) and `preemptionPolicy: Never`. Otherwise the Priority admission plugin refuses every pod. Observed live on 2026-08-28 (`graded/policies/cage-tier.yaml:106-124`). Served 2.0.0 to 3.0.0 broke on exactly this and were retired (3dab34d). If v8 keeps eviction priority, it must ship the PriorityClasses with matching names; v7's are version-suffixed (9bd904e). If v8 drops priority, drop all three fields. Priority is not something a probe sees.
2. **The privileged pair.** `privileged: false` must be written in the same securityContext as `allowPrivilegeEscalation: false`. Otherwise the API server rejects the pod (`cage-tier.yaml:88-92`, observed live).
3. **Host namespaces clobbered shut.** `hostNetwork: true` walked out of `isolated`, because NetworkPolicy does not apply to host-network pods (`cage-tier.yaml:94-99`, observed live). A network probe on such a pod reads "open" at every rung.
4. **Tighten-only.** Limits are the minimum of the pod's own and the rung's, never an overwrite (`cage-tier.yaml:70-74`, `:259-264`). Security flags are ORed with what the pod declared (`:59-68`, `:268-271`).
5. **UPDATE must be byte-identical or labels-only.** The served body matches CREATE and UPDATE (`v7.0.0/cage-tier.yaml:20-22`) and reads the Namespace each time. After a Namespace rung move, any UPDATE to a pod still running on the old rung writes different, immutable fields (priority, priorityClassName, container limits, a new sidecar container). The API server refuses it, which `cage-tier.yaml:76-86` calls "a refusal by another name". Commit de95c11 split the machinery into a full body on CREATE and labels-only on UPDATE, but the served cage-tier was never split. A moving ratchet makes this load-bearing. **Not observed.** v8: full body on CREATE, labels-only re-assertion on UPDATE. Re-cage by rollout: the target stamps the rung onto Deployments.
6. **Reach: all restricting rungs generated up front, synchronize off.** On Kyverno 1.18, a GeneratingPolicy with synchronize on called DeleteDownstreams for the whole policy and wiped every other Namespace's `cage-reach-*`. A tier move also opened a window with no NetworkPolicy at all (`graded/policies/cage-netpol.yaml:25-56`, observed live 2026-08-28). One owner per downstream name (de95c11 R5). The upgrade path its own header names, static NetworkPolicies per governed Namespace (`:55-56`), would remove the generator and its hazard.
7. **`matchConditions`, not `matchConstraints.objectSelector`.** Kyverno flattens objectSelector into one shared webhook configuration, last reconciled wins, which breaks coexistence (`v7.0.0/cage-tier.yaml:1-4`). This matters during the v7-to-v8 cut-over. Whether a `namespaceSelector` has the same problem: could not determine.
8. **One mutating policy writes the cage.** Two mutating policies writing cage fields produced a pod labelled `isolated` carrying cage-baseline's PriorityClass (measured with kyverno 1.18.2; 553137f). If v8 scopes by governed Namespace (item 10), it overlaps v7's claimants and the machinery cages. Disjoint-by-claim is then impossible, so the cut-over must be **one change**: v7 bodies and machinery out, v8 in, and the pods recreated.
9. **Keep the substrate alive.** CoreDNS and other system pods stay running because of the claim gate and because substrate Namespaces are never governed (`cage-tier.yaml:31-37`; 3d7f098, which found that a `|| true`-loosened gate passed while the engine caged CoreDNS at isolated). Any v8 scope change must keep one of the two bars, with a test.
10. **Scope: who cages an unclaimed pod.** v7 cage-tier cages only pods claiming `7.0.0`. Two cases are caged at the bottom rung only by machinery from `versions.yaml`: an unclaimed pod in a governed Namespace (`governed-namespace-requires-claim`) and a pod claiming an undeclared version (`policy-version-orphan-cage`) (9bd904e, 553137f). If the machinery is parked without a replacement, both run uncaged. v8 should match every pod in a governed Namespace, so one body covers both cases.
11. **initContainers.** cage-tier hardens `containers` only. The machinery's `cage_body.py:17-21` extends hardening to initContainers ("measured on kyverno 1.18.2"). v8 should do the same, or the probe reports what the main container cannot do while an initContainer ran privileged.
12. **Known holes to name in `rungs.yaml`, not hide.** A hostPath volume cannot be removed by an apply patch (`cage-tier.yaml:100-104`). `runAsUser: 0` beside a forced `runAsNonRoot` gives "admitted, caged, does not start" (`cage_body.py:23-28`). The target's serving check must read that as `serving-lost`, not as a closed capability.
13. **Probe lessons from the live tail** (`graded/verify-graded.sh:630-670`). Grade reach on a connection, not a YAML read. A YAML-shape check passed while a host-network pod escaped and while other Namespaces' reach had just been deleted (`:633-637`). Poll, because the generated NetworkPolicy has to be programmed by the CNI and there is a window between admission and the reach cage (`:651-663`). Bracket with a pod that should reach (`:666-669`: the baseline pod reaching the API server), so that "cannot reach" is not vacuous. That is the target's reference pod.
14. **Engine pin and API version.** Test v8 with the CLI for the engine driftwood declares (1.18.2, checksum in `engine/kyverno/engine-table.yaml`), not with whatever is on PATH. Carry e0b6f9f's fix: `policies.kyverno.io/v1` and a `string()` cast on the tier label.
15. **Serving for each rung, which sets the target's range.** Reach for each rung (`graded/policies/cage-netpol.yaml:9-17`, `:108-117`):
    - **baseline:** no NetworkPolicy, full reach.
    - **restricted and quarantine:** ingress only from pods in the same Namespace; egress only UDP 53 to kube-system.
    - **isolated:** nothing in, nothing out.

    driftwood's workloads listen on ports: `storefront.yaml` port 80, `api.yaml` port 8080, `pod.yaml` nginx. They are bare Pods, all claiming `7.0.0`. Anything serving them from outside their own Namespace, such as an ingress controller or a user, loses them at the first notch above baseline. With today's reach design, the measured "tightest rung on which the workload still serves" is therefore baseline, unless the serving check runs from inside the Namespace. Separately, `storefront` binds port 80 as `runAsUser: 101`. At a hardened rung all capabilities are dropped, so whether it can still bind depends on the runtime's unprivileged-port setting: could not determine. The sampler records it Running at isolated, which is not the same as serving. v8's reach design must be chosen with the serving check in view.
